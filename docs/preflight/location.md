# Preflight: location and GPS

Source-reconciled September 30, 2026 by Codex/Astra. Start with [MAIN location/snapshot trace](../architecture/ai-pipeline.md#2-gps-preparation-and-explicit-strategy-admission), [location architecture](../architecture/LOCATION.md) and [Google API contracts](../architecture/google-cloud-apis.md).

- Current driver position comes from a fresh browser GPS observation with reported accuracy and timestamp, validated by [coordinates.js](../../shared/coordinates.js). No IP, home address, hardcoded city or guessed timezone substitutes for current GPS.
- Preserve supplied coordinate precision in requests and storage. [coordsKey](../../server/lib/location/coords-key.js) formats a six-decimal lookup key; decimal count is not sensor accuracy. Zero latitude/longitude is valid, so truthiness checks are inappropriate.
- [main-run-snapshot.js](../../server/lib/location/main-run-snapshot.js) owns authenticated portal capture. Current browser flow posts `captureId` and fresh GPS to `/api/location/snapshot` before preference confirmation, then prepares Briefing and confirms canonical setup. Validate the live owner/session and current capture before publication. A concurrent loser receives the saved winner's coordinates, timestamp and accuracy together. Legacy `runId` capture retains strict admission/settings checks.
- Explicit Strategy Continue/Refresh consumes prepared context through `expectedSnapshotId`, pins canonical settings/rules and preserves original source timestamps/generation in a new downstream context. It does not recapture GPS. [GlobalHeader](../../client/src/components/GlobalHeader.tsx) Refresh prepares location and Briefing first, then admits Strategy only with confirmed canonical preferences.
- First-session GPS starts only after setup confirms no saved or pending context. Focus/navigation/remount restore same-session saved context through reads; unfinished preparation requires manual Refresh. Preserve account/token/session fences and ensure a delayed error for an old snapshot cannot cancel a newer capture.
- Timezone is resolved from coordinates via the shared Google transport. Market identity is a separate country/state-scoped lookup; market timezone is not a location fallback.
- Google Places New supplies verified coordinates, identity, address and opening information through requested fields. Verified venue IANA timezone comes from stored venue coordinates via the Google Time Zone API. Preserve a resolved place ID through enrichment. Routes returns measurements and per-element failure states; a failed cell is not a zero-minute trip.
- Venue opening and event clock interpretation use the verified venue's IANA zone. Display windows use the explicitly selected viewer/snapshot zone. Neither may silently use the machine's local timezone. Missing timezone is unknown or failure, not UTC by default.
- [hours](../../server/lib/venue/hours/index.js) supplies local schedule evaluation. Check current consumer provenance: an explicit provider current-opening observation and a parsed regular schedule are different evidence. Do not invent open/closed state from missing fields.
- Independent Concierge/Bars requests have their own capture/cache lifecycle. Do not reuse their public token, stale GPS receipt or circuit state as authenticated MAIN admission.

Before editing, trace producer, saved fields, consumer, cancellation and account changes. Run relevant [location](../../tests/location/), [venue](../../tests/venue/) and client capture tests.
